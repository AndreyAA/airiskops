**Цель**
MVP должен выявлять возможные согласованные `prompt injection` атаки по семантически похожим пользовательским запросам, если такие запросы приводят к серии сработок `PROMPT_INJECTION` в пределах окна `5m`.

**Бизнес-контекст**
Текущий MVP показывает отдельные findings, оконные агрегаты и базовые incident signals, но не отвечает на вопрос, являются ли несколько PI-сработок частью одной повторяющейся атакующей кампании. Из-за этого риск-команда позже замечает массовые паттерны, тратит больше времени на разбор разрозненных кейсов и хуже приоритизирует расследование.

**Business Value**
После внедрения capability команда должна получить:
- раннее выявление повторяющихся `prompt injection` кампаний;
- снижение числа разрозненных PI-сигналов в triage;
- более быстрый переход от детектора к расследованию;
- видимость не только факта PI-сработки, но и признаков координированной атаки.

**Scope MVP**
В первую версию входят только:
- `guardrailName = PROMPT_INJECTION`
- только события с `triggered = true`
- окно анализа `5m`
- сравнение событий из разных `sessionId`
- использование embedding исходного пользовательского запроса
- выпуск отдельного campaign-level incident

**Режимы детекции**
Система должна поддерживать два режима:
- `GLOBAL` — анализ похожих PI-сработок среди всех агентов.
- `PER_AGENT` — анализ похожих PI-сработок отдельно внутри каждого `agentId`.

Активный режим должен задаваться конфигурацией в `YAML`.

**Out Of Scope**
В первую версию не входят:
- другие guardrail-ы;
- cross-window correlation;
- автоматическое обучение новых классов атак;
- сложная онлайн-кластеризация;
- автоматическое блокирование пользователя, сессии или агента;
- полноценная SIEM/case-management orchestration.

**Функциональные требования**
1. Система должна анализировать triggered-события `PROMPT_INJECTION` в пределах окна `5m`.
2. Система должна использовать embedding исходного пользовательского запроса как основной признак семантической близости сработок.
3. Система должна выявлять группу похожих PI-сработок, если группа покрывает не менее заданного числа различных `sessionId`.
4. Система должна интерпретировать такую группу как возможную согласованную атаку.
5. Система должна поддерживать два режима campaign detection: `GLOBAL` и `PER_AGENT`.
6. В режиме `GLOBAL` поиск должен выполняться по событиям всех агентов в пределах окна `5m`.
7. В режиме `PER_AGENT` поиск должен выполняться отдельно для каждого `agentId` в пределах окна `5m`.
8. Система должна формировать отдельный campaign-level incident, а не только набор сырых findings.
9. Система должна сохранять связь incident с исходными `requestId`, `sessionId`, `agentId` и, если доступно, `userId`.
10. Система должна предоставлять representative example запроса или эквивалентный explainability anchor для расследования.
11. Система должна поддерживать настройку чувствительности правила через конфигурационные параметры в `YAML`.
12. Система должна выпускать не более одного campaign incident на одно окно для каждого scope анализа.
13. Система должна уменьшать alert fatigue за счёт объединения однотипных PI-сработок в один operational signal.
14. Система должна быть пригодна для replay-проверки на воспроизводимых сценариях.

**Нефункциональные требования**
1. Решение должно укладываться в текущую near-real-time модель MVP.
2. Логика должна быть достаточно простой для объяснения risk-команде, аудиторам и стейкхолдерам.
3. Первая версия не должна требовать отдельной тяжёлой ML-платформы.
4. Использование исходных пользовательских запросов должно учитывать ограничения по чувствительным данным.
5. Поведение детектора должно быть детерминированным и воспроизводимым на одинаковом входе.

**Требования к данным**
Для участия события в campaign-анализе должны быть доступны:
- `eventTime`
- `requestId`
- `sessionId`
- `PROMPT_INJECTION`
- `triggered = true`
- embedding исходного пользовательского запроса

Дополнительно:
- в режиме `PER_AGENT` обязателен `agentId`
- в режиме `GLOBAL` должен сохраняться список `agentId`, вошедших в incident
- желательно иметь `userId`
- желательно иметь исходный текст запроса в полном или безопасно-маскированном виде
- желательно иметь `confidence` исходного finding

**Требования к конфигурации**
Параметры campaign detection должны задаваться в `YAML`.

Минимально конфиг должен позволять задавать:
- `enabled`
- `mode`: `GLOBAL | PER_AGENT`
- `window`
- `minGroupSize`
- `topKSeeds`
- `maxCosineDistance`
- `severityByGroupSize`

Пример:
```yaml
promptInjectionCampaign:
  enabled: true
  mode: GLOBAL
  window: 5m
  minGroupSize: 3
  topKSeeds: 3
  maxCosineDistance: 0.12
  severityByGroupSize:
    low:
      min: 3
      max: 4
    medium:
      min: 5
      max: 7
    high:
      min: 8
      max: 11
    critical:
      min: 12
```

**Требования к severity**
`Severity` должна определяться конфигурацией и зависеть от размера найденной группы.
Для MVP достаточно ruleset в `YAML`, где severity вычисляется только по `groupSize`.

**Требования к выходному инциденту**
Campaign incident должен содержать как минимум:
- `incidentType`
- `detectionMode`
- `windowStart`
- `windowEnd`
- `groupSize`
- `uniqueSessionCount`
- `requestIds`
- `sessionIds`
- `severity`
- `representativeRequest`
- `explanation`

Дополнительно:
- для `GLOBAL` — `agentIds`
- для `PER_AGENT` — `agentId`

**Требования к доступности результата**
Campaign incidents должны быть доступны:
- в Grafana как новый тип инцидента;
- через `REST` API для получения списка инцидентов;
- через `REST` API для просмотра содержимого конкретного инцидента.

**Критерии готовности**
Capability считается готовой для MVP, если:
1. На replay-сценарии согласованной атаки система поднимает campaign-level incident.
2. На одиночных и несвязанных PI-сработках система не формирует такой incident либо делает это заметно реже.
3. Аналитик может перейти от incident к связанным `requestId`, `sessionId` и, при необходимости, `agentId`.
4. В Grafana виден новый тип инцидента и его базовые характеристики.
5. Через `REST` можно получить список campaign incidents и содержимое конкретного incident.
6. Параметры чувствительности и severity настраиваются через `YAML`.
7. Команда может показать практический business outcome: обнаружение повторяющейся атаки, а не только рост числа PI-findings.

**Почему в будущем могут понадобиться несколько инцидентов на окно**
Несколько campaign incidents в одном окне могут понадобиться, если одновременно идут:
- две или более независимых атакующих кампаний;
- разные prompt patterns, не похожие друг на друга;
- независимые группы по разным агентам или по разным техникам атаки.

В MVP это сознательно не включается, чтобы сохранить простую и объяснимую semantics: один наиболее значимый campaign incident на окно для каждого scope анализа.

**Открытые вопросы**
1. Нужен ли полный текст запроса в incident, или достаточно masked form / representative reference?
2. Какой стартовый `minGroupSize` лучше считать бизнес-значимым: `3`, `4` или `5`?
3. Должен ли `REST` API возвращать только активные incidents или также историю за период?
4. Нужен ли отдельный retention/доступ-контроль для текста запросов и representative prompt?
