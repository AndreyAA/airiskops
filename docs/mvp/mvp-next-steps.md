**Самый выгодный следующий шаг — сделать MVP измеримым и проверяемым при сбоях, затем добавить один законченный бизнес-сценарий.** Для этого уже есть большая часть основы: генераторы, collector, оконные тесты, инциденты, политики и dashboards.

Я бы выделил **11–19 человеко-дней на основной пакет**, или **14–25 с резервом**. Он существенно усилит доказательства для руководства: корректность результатов, реальная задержка, восстановление после сбоя и обнаружение эксплуатационных проблем.

Это заметно меньше расширенного банковского PoC из отчёта, потому что речь о локальных проверках. Производительность на 50K сообщений/с, банковская отказоустойчивость и качество реальных guardrails останутся отдельными задачами.

## 2. Самое дешёвое и полезное: улучшить доказательность НТ

### 2.1. Исправить collector и добавить паспорт эксперимента

Здесь есть конкретные небольшие доработки.

В [nt_report_collector.py](/home/bob/old_bob/IdeaProjects/airiskops/tools/reporters/nt_report_collector.py:113) Kafka consumer group жёстко задана как `airiskops-mvp`. Между тем ONNX-профиль использует другую группу. Сравнение профилей может получить lag чужой job либо ошибку сбора.

В функции [assess()](/home/bob/old_bob/IdeaProjects/airiskops/tools/reporters/nt_report_collector.py:212) отсутствующие значения некоторых метрик трактуются через `or 0`. Сама функция допускает оценку `stable` без подтверждения полноты этих измерений.

**Что добавить:**

- consumer group из фактической конфигурации;
- статус `inconclusive` — «данных недостаточно»;
- обязательный набор метрик и проверку их свежести;
- раздельные интервалы: прогрев, нагрузка, догоняние очереди;
- фактическую длительность генерации;
- commit, JAR hash, effective config, image identifiers;
- parallelism операторов, CPU/RAM limits и характеристики диска;
- сохранение raw JSON и краткого итогового отчёта в одном каталоге.

Чувствительные параметры конфигурации при сохранении нужно исключать.

**Критерии готовности:**

1. DEFAULT и ONNX измеряют lag собственных групп.
2. При отсутствии обязательной метрики результат — `inconclusive`.
3. Другой инженер может воспроизвести прогон по сохранённому пакету.
4. Отчёт различает заданные запросы/с и фактически опубликованные сообщения/с.

**Что закрывает:** ⚠️ методику нагрузочного тестирования.
**Что останется:** ❌ доказательство 50K сообщений/с.

**Почему это первый приоритет:** любая последующая оптимизация станет сравнимой с baseline.

### 2.2. Увеличить длительность существующих прогонов

Для первого улучшения результатов не нужен новый кластер.

После исправления измерений выполнить:

- 10–15 минут на заведомо комфортной нагрузке;
- несколько ступеней до появления устойчивой деградации;
- 30–60 минут на выбранной рабочей ступени;
- повтор одинаковой нагрузки на DEFAULT/RocksDB;
- сравнение с включённой и выключенной similarity.

Фиксировать фактический вход, рост очереди, время догоняния и состояние. Нулевой lag после завершения ещё не доказывает соблюдение latency во время прогона.

**Ценность:** вместо минутного наблюдения появится воспроизводимый диапазон работы конкретного локального стенда.

## 3. Внешний проверяющий consumer — основа нескольких улучшений сразу

Сейчас smoke-проверки во многом отвечают на вопрос «в topic появились данные». Для обоснования внедрения нужен следующий уровень:

> Какие именно данные появились, сколько раз, с какой задержкой и соответствуют ли они сценарию?

### Минимальная реализация

Добавить небольшой инструмент в `tools`, который:

1. Читает тестовый manifest с ожидаемыми событиями и результатами.
2. Фиксирует границы прогона по offsets и идентификаторам.
3. Читает outputs Kafka.
4. Сверяет результаты.
5. Выпускает отчёт о пропусках, повторах, неожиданных результатах и задержках.

Для локального объёма достаточно файлов и SQLite. Отдельная промышленная БД не нужна.

### Что сравнивать

| Выход | Проверка |
|---|---|
| `normalized-events` | Ожидаемые события присутствуют; повторы посчитаны |
| `invalid-events` | Каждое специально испорченное событие попало в нужный маршрут |
| `late-events` | Проверены события за пределом согласованного допуска |
| `guardrail-aggregates` | Итог по ключу и окну совпадает с эталоном; повторные выпуски учтены |
| `basic-incidents` | Правильные rule, severity, связанные requests и версии политики |

**Важно:** эталон должен вытекать из спецификации. Копирование логики Java в Python создаст две реализации одной ошибки.

Для начала достаточно **20–30 небольших вручную проверенных сценариев**: нормальный поток, пороги правил, границы окон, late events, дубликаты, смена политики.

### Как измерять задержку дёшево

Для тестового потока можно хранить время отправки и идентификаторы во внешнем manifest, не меняя сразу production event schema.

Измерять отдельно:

- отправка генератором → чтение normalized output;
- отправка события, достаточного для инцидента → чтение инцидента;
- конец event-time окна → получение агрегата.

Время отправки генератором включает его собственные очереди. Называть его «Kafka ingest timestamp» нельзя. Для более точной границы понадобится подтверждение producer и подходящая настройка timestamps.

Отчёт должен показывать p50/p95/p99 **вместе с числом измерений и недоставленных результатов**. Иначе потерянные события искусственно улучшат latency.

**Оценка:** 3–5 дней для базового локального инструмента.

**Ценность:** этот consumer затем используется для НТ, recovery, EXACTLY_ONCE и демонстрации бизнес-результата. Это одна из наиболее окупаемых доработок.

## 4. Закрыть дешёвые gaps корректности

### 4.1. Проверить метрики при повторной выдаче окна

В [GuardrailWindowProcessFunction](/home/bob/old_bob/IdeaProjects/airiskops/flink-job/src/main/java/com/bank/airiskops/app/functions/GuardrailWindowProcessFunction.java:202) при каждом выпуске агрегата выполняется:

```java
eventsCounter.inc(aggregate.totalEvents());
```

Например:

- окно выпустило итог `100`;
- пришло допустимо позднее событие;
- окно выпустило новый итог `101`;
- counter увеличился на `201`.

Это корректно как «сумма объёма опубликованных snapshots», но неверно как «обработано 201 уникальное событие».

Повторные выпуски при allowed lateness предусмотрены Flink. Поэтому нужно согласовать смысл метрик, а не запрещать late events ради удобного счётчика. [Apache Flink: Windows](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/dev/datastream/operators/windows/).

**Дешёвое решение:**

- счётчики поступления вести на входе соответствующей ветки;
- число выпусков оставить отдельным counter;
- значения последнего агрегата показывать как gauges;
- проверить названия и запросы существующих dashboards;
- добавить сценарий `100 → 101`, проверяющий именно бизнес-интерпретацию.

Это также означает: operational counters не следует выдавать за аудируемое число уникальных событий после recovery.

### 4.2. Проверить очистку сессии при нарушении порядка

В [PolicyAwareSessionIncidentEvaluatorFunction](/home/bob/old_bob/IdeaProjects/airiskops/flink-job/src/main/java/com/bank/airiskops/app/functions/PolicyAwareSessionIncidentEvaluatorFunction.java:122) deadline вычисляется из времени текущего события.

Если после нового события приходит старое, deadline может переместиться назад.

**Минимальная работа:**

- описать ожидаемый смысл inactivity timeout;
- добавить последовательности `новое → старое`, повтор, событие на границе timeout;
- при подтверждении спецификацией рассчитывать deadline от максимального времени активности.

Изменение нескольких строк возможно, но сначала нужно согласовать семантику.

### 4.3. Не путать общий dedup с уникальным request ID

Один request закономерно создаёт несколько findings. Дедупликация только по `requestId` потеряет корректные события.

Для локального verifier можно использовать manifest и специально уникальные тестовые записи. Для общей production-дедупликации потребуется контракт идентичности события: отдельный event ID либо согласованный составной ключ.

**Оценка блока проверок корректности:** 2–3 дня, если решения по семантике приняты.

**Ценность:** исключение ложных улучшений НТ и ложных рисковых показателей.

## 5. Recovery и EXACTLY_ONCE: локально доказать можно недорого

### 5.1. Начать с одного отказа: падение TaskManager

Полный chaos framework здесь избыточен. Достаточно воспроизводимого сценария:

1. Запустить поток с известными идентификаторами.
2. Дождаться успешного checkpoint.
3. Остановить процесс/контейнер TaskManager в отдельном тестовом окружении.
4. Восстановить TaskManager.
5. Дождаться восстановления и догоняния.
6. Сверить результаты внешним consumer.

Нужны сохранённые checkpoint, вход Kafka и фиксированная конфигурация. JobManager в этом первом сценарии остаётся работающим.

Измерять:

- время обнаружения сбоя;
- время восстановления обработки;
- время возврата очереди к норме;
- пропуски и повторы;
- корректность stateful-результатов.

**Оценка:** 3–5 дней с автоматизацией и проверкой.

**Покрытие после:** ✅ восстановление после конкретного локального отказа.
**Останется:** ❌ потеря всего хоста, HA JobManager, отказ площадки.

Полезное уточнение: existing `recovery-seconds` в нагрузочном wrapper — время ожидания догоняния, а не проверка восстановления после падения.

### 5.2. После этого добавить EXACTLY_ONCE-профиль

Изменений относительно немного:

- значение `EXACTLY_ONCE` в конфигурационной модели;
- transactional ID prefix для каждого sink и экземпляра deployment;
- согласованные transaction/checkpoint timeouts;
- проверяющий consumer с `read_committed`;
- отдельный профиль запуска;
- сценарии падения до и после фиксации.

Prefix должен исключать конфликты одновременно работающих jobs и сохранять корректную идентичность при восстановлении.

Flink Kafka sink фиксирует транзакции на checkpoint, поэтому обязательно сравнить задержку видимости outputs. [Apache Kafka connector](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/connectors/datastream/kafka/).

**Оценка:** ещё 2–4 дня после готовности recovery/verifier.

**Что можно честно заявить:** проверена гарантия Kafka → Flink → Kafka для обозначенных отказов и входного сценария.

**Что это не закрывает:**

- дубликаты, которые сам producer записал как разные входные события;
- атомарность Kafka и внешнего HTTP-действия;
- повторные блокировки downstream;
- потерю single-node Kafka вместе с хостом.

Для MVP это всё равно сильное доказательство, существенно дешевле полного банковского контура.

## 6. Улучшить производительность: сначала небольшое изменение без смены результата

### 6.1. Убрать повторную сортировку

Сейчас [calculatePercentiles()](/home/bob/old_bob/IdeaProjects/airiskops/flink-job/src/main/java/com/bank/airiskops/app/functions/GuardrailWindowProcessFunction.java:166) отдельно рассчитывает p50/p95 для двух списков. Каждый вызов создаёт копию и сортирует её.

Можно:

- один раз отсортировать все confidence;
- взять из него p50 и p95;
- один раз отсортировать triggered confidence;
- взять из него оба перцентиля.

**Оценка:** 0,5–1 день.

**Проверка:** совпадение результатов на пустых списках, границах ранга, одинаковых значениях и случайных наборах; затем профиль CPU/allocations.

Число сортировок уменьшится с четырёх до двух. Это **не обещание двукратного ускорения pipeline**: доля этой работы пока не измерена.

### 6.2. Затем решать проблему размера state

[Accumulator](/home/bob/old_bob/IdeaProjects/airiskops/flink-job/src/main/java/com/bank/airiskops/app/functions/GuardrailAggregateAccumulator.java:44) сохраняет все confidence. Повторная сортировка — только часть стоимости; сами списки продолжают расти.

Если для управленческой аналитики допустим приближённый confidence percentile, кандидат — фиксированная гистограмма.

Например, после согласования диапазона confidence `[0,1]`:

- интервалы шириной `0,001`;
- массив счётчиков вместо списка всех значений;
- отдельная гистограмма triggered confidence;
- оговорённая погрешность по значению.

Две гистограммы примерно на тысячу `long`-счётчиков занимают около **16 KB полезных массивов на accumulator**. Для маленьких окон это может быть дороже списков; для больших объём становится ограниченным. Сериализацию массива при обновлении также нужно измерить.

**Оценка:** 3–5 дней.

**Условия:**

- согласовать погрешность и контракт метрики;
- проверить конечность и диапазон confidence;
- оценить миграцию state;
- сравнить CPU, serialized bytes, checkpoint и результаты.

Если нужны строго точные перцентили, заменять их приближёнными ради скорости нельзя.

## 7. Добавить две функции, понятные бизнесу

### 7.1. Карточка расследования — самая дешёвая демонстрация ценности

Сейчас инциденты уже существуют. Не требуется заново строить incident layer, хотя старый `near-term-improvement-plan.md` ещё предлагает его как будущую работу.

Можно добавить локальный инструмент, который по `incidentId` собирает:

- правило и severity;
- связанные requests и findings;
- временную последовательность;
- версии policy/guardrail/model, где они доступны;
- причину срабатывания;
- ссылки на ограниченные evidence;
- задержку обнаружения.

Формат — HTML или Markdown, генерируемый из локально собранных Kafka outputs. Начинать с отдельного web-приложения необязательно.

**Оценка:** 2–4 дня после готовности consumer.

**Критерий:** человек, не знакомый с кодом, может объяснить, почему появился инцидент и какие события это подтверждают.

**Business value:** демонстрация сокращения времени расследования. Само сокращение нужно измерить на нескольких одинаковых кейсах вручную и с карточкой.

Это **⚠️ частичное закрытие аудита**, а не неизменяемый промышленный журнал.

### 7.2. Контроль отсутствующих findings — наиболее полезная новая функция

Для AISafety Ops отсутствие сработок неоднозначно:

- атак нет;
- detector перестал отправлять результаты;
- интеграция потеряла события.

MVP сейчас лучше видит поступившие findings, чем отсутствие ожидаемых.

**Предлагаемый сценарий:**

> После завершения запроса за установленное время должны поступить результаты обязательных guardrails. Если часть отсутствует, появляется технический инцидент о неполной проверке.

Понадобятся:

- перечень ожидаемых guardrails;
- ключ `tenantId + requestId`;
- request/response и поступившие findings;
- срок ожидания;
- правила обработки позднего результата и повтора;
- ограниченное состояние.

Для первой версии достаточно keyed correlation с timer. Если цель — именно проверить Flink join API, сделать отдельный interval-join эксперимент; собственная корреляция не закрывает этот API-gap автоматически.

**Оценка:** 4–6 дней.

**Критерии:**

- все обязательные findings пришли — инцидента нет;
- один отсутствует — один инцидент;
- повтор finding не создаёт лишних результатов;
- late finding обрабатывается согласно согласованному правилу;
- совпадающие request IDs разных tenants не смешиваются.

**Ценность:** контроль работоспособности самой защиты. Для этого не нужна новая ML-модель.

## 8. Эксплуатация, безопасность и другие недорогие дополнения

### Работающие alerts: 1–2 дня

Достаточно пяти условий:

1. Job или exporter недоступны.
2. Успешного checkpoint давно нет.
3. Растёт очередь.
4. Backpressure держится выше порога.
5. Растёт доля invalid/detector errors.

Добавить локальный Alertmanager с webhook-приёмником, журналирующим доставку. Пороговые правила и доставка уведомлений — отдельные части механизма Prometheus. [Prometheus: Alerting overview](https://prometheus.io/docs/alerting/latest/overview/).

Проверка — искусственно вызвать каждый случай и подтвердить firing/resolved. Сразу подключать реальные каналы сотрудников для локального MVP необязательно.

### Tenant-aware ключи: 2–4 дня

Польза высокая, но это изменение распределения и структуры keyed state.

Нужно определить:

- обязателен ли `tenantId`;
- допустим ли fallback для старых событий;
- какие aggregate/session/incident IDs меняются;
- как поступаем с существующим state.

Для одноразового синтетического стенда миграция может быть простой. Для сохранённого рабочего state это уже отдельная задача.

**После:** ✅ изоляция проверена на конкретных коллизиях ключей; банковская tenant isolation целиком остаётся ⚠️.

### Минимизация payload: 2–4 дня

Недорогая цель — исключить ненужное копирование текста:

- явная allowlist полей нормализованного события;
- режим хранения raw payload;
- ограничение evidence;
- отдельный подход к invalid/late outputs;
- проверка синтетическими «секретами», что они не размножились по запрещённым выходам.

Простое удаление `rawPayload` не означает, что PII исчезла: она может находиться в evidence, идентификаторах и ошибках.

### SQL-эксперимент: 1–2 дня

Реализовать один агрегат `count/sum/min/max` на SQL вне основной topology и сравнить:

- время реализации;
- число необходимых изменений при новом измерении;
- результаты на одинаковом упорядоченном dataset;
- отдельные сценарии опоздания.

Полную эквивалентность SQL и текущего DataStream с late revisions заранее обещать нельзя.

**После:** ✅ появляется практический опыт SQL; переписывание всего pipeline не требуется.

## 9. Что я бы пока отложил

| Идея | Причина отложить |
|---|---|
| Kubernetes и полноценный HA локально | Большой объём платформенной работы; сначала полезнее доказать recovery и правильность |
| Новый vector database / ANN | Сначала измерить фактическое число clusters и долю времени поиска |
| GPU-инфраструктура | Нет baseline реального ONNX inference и целевой доли PI-трафика |
| Собственный DSL и редактор правил | Уже есть политики; пока выше ценность их проверки и объяснения результата |
| Добавление множества типов окон | Увеличивает поверхность проверки без нового бизнес-сценария |
| Всеобщий dedup по `requestId` | Может удалить корректные findings |
| «PII detector» на нескольких regex | Проверит интеграцию, но не докажет качество банковского PII-контроля |
| Принудительный переход на RocksDB | Backend не устраняет неограниченные коллекции и горячие ключи |
| Достижение красивой цифры RPS снижением guarantees | Такой результат плохо сопоставим с целевым сценарием |

## 10. Рекомендуемый порядок и итоговая ценность

### Основной пакет: 11–19 человеко-дней

1. Паспорт НТ и корректная оценка полноты измерений.
2. Внешний consumer/verifier и задержка доставки.
3. Проверки late events и смысла бизнес-метрик.
4. Один автоматизированный recovery-сценарий.
5. Работающие локальные alerts.
6. Устранение повторной сортировки.

С резервом: **14–25 человеко-дней**. Для двух знакомых с проектом инженеров — ориентировочно **2–3 календарные недели**, с учётом зависимостей и проверок.

### После — один пакет по цели

| Главный вопрос | Следующая инвестиция |
|---|---|
| «Можно ли доверять доставке?» | EXACTLY_ONCE-профиль, 2–4 дня |
| «Какую пользу получит риск-команда?» | Карточка расследования, 2–4 дня |
| «Контролируем ли мы саму защиту?» | Missing-findings correlation, 4–6 дней |
| «Почему падает производительность?» | Измерение state и ограниченные перцентили, 3–5 дней |
| «Насколько трудно разрабатывать?» | SQL-эксперимент, 1–2 дня |

**Мой выбор:** основной пакет → карточка расследования → EXACTLY_ONCE → контроль отсутствующих findings. Работу над state поднять раньше, если обновлённые измерения подтвердят её как основной bottleneck.

После этого MVP сможет показать руководству законченную последовательность:

> Запрос обработан → необходимые проверки проконтролированы → инцидент объяснён → задержка измерена → сбой воспроизведён → восстановление и результат проверены.

Это существенно усилит основание для банковского PoC. При этом статусы **50K сообщений/с, production HA, качество банковских детекторов и предотвращение утечек до выдачи ответа** должны оставаться открытыми до соответствующих испытаний.
