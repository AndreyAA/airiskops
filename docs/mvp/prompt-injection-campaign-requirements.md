# Prompt Injection Campaign Detection Requirements

Дата актуальности: 2026-09-04

## Назначение

Этот документ фиксирует согласованные business requirements для MVP-capability, которая выявляет возможные согласованные `prompt injection` атаки по семантически похожим пользовательским запросам.

Документ описывает:

- какую бизнес-проблему решает capability;
- что входит и не входит в MVP;
- какие режимы детекции поддерживаются;
- какие данные, outputs и интерфейсы обязательны;
- по каким критериям MVP считается готовым.

## Бизнес-контекст

Текущий AIRiskOps MVP уже умеет:

- принимать и нормализовывать события агентов и guardrail findings;
- строить оконные агрегаты;
- формировать базовые incident signals;
- показывать результаты в Kafka, Prometheus и Grafana.

При этом текущий контур не отвечает на отдельный вопрос operational risk:

- являются ли несколько `PROMPT_INJECTION` сработок частью одной повторяющейся атакующей кампании.

Из-за этого risk-команда:

- позднее замечает массовые attack patterns;
- тратит больше времени на разбор разрозненных кейсов;
- хуже приоритизирует triage;
- медленнее адаптирует guard и policy под наблюдаемую технику атаки.

## Цель MVP

MVP должен выявлять возможные согласованные `prompt injection` атаки, если в течение окна `5m` наблюдается группа семантически похожих пользовательских запросов, которые приводят к triggered-сработкам `PROMPT_INJECTION` в разных пользовательских сессиях.

## Business Value

После внедрения capability команда должна получить:

- раннее обнаружение повторяющихся `prompt injection` кампаний;
- уменьшение числа разрозненных PI-сигналов в triage;
- более быстрый переход от detector findings к расследованию;
- видимость не только факта PI-сработки, но и признаков координированной атаки.

## Scope MVP

В первую версию входят только:

- `guardrailName = PROMPT_INJECTION`;
- только события с `triggered = true`;
- окно анализа `5m`;
- анализ похожих событий из разных `sessionId`;
- использование embedding исходного пользовательского запроса;
- выпуск отдельного campaign-level incident;
- просмотр активных incidents через `REST`;
- отображение нового типа incident в Grafana.

## Out Of Scope

В первую версию не входят:

- другие guardrail-ы;
- cross-window correlation;
- автоматическое обучение новых классов атак;
- сложная online-кластеризация;
- автоматическое блокирование пользователя, сессии или агента;
- полноценная SIEM- или case-management orchestration;
- historical `REST` API для архивных incidents.

## Режимы детекции

Система должна поддерживать два режима campaign detection:

- `GLOBAL` — анализ похожих PI-сработок среди всех агентов;
- `PER_AGENT` — анализ похожих PI-сработок отдельно внутри каждого `agentId`.

Активный режим должен задаваться конфигурацией в `YAML`.

### Семантика `GLOBAL`

- в анализ попадают события всех агентов;
- сигнал означает, что в окне `5m` найдена группа похожих PI-сработок из разных `sessionId`, независимо от `agentId`;
- incident должен содержать список `agentIds`, попавших в найденную группу.

### Семантика `PER_AGENT`

- анализ выполняется отдельно для каждого `agentId`;
- сигнал означает, что в окне `5m` найдена группа похожих PI-сработок из разных `sessionId` внутри одного агента;
- incident должен содержать один `agentId`.

## Функциональные требования

1. Система должна анализировать только triggered-события `PROMPT_INJECTION` в пределах окна `5m`.
2. Система должна использовать embedding исходного пользовательского запроса как основной признак семантической близости между PI-сработками.
3. Система должна выявлять группу похожих PI-сработок, если группа покрывает не менее заданного числа различных `sessionId`.
4. Система должна интерпретировать такую группу как возможную согласованную атаку.
5. Система должна поддерживать режимы `GLOBAL` и `PER_AGENT`.
6. Активный режим детекции должен задаваться конфигурацией в `YAML`.
7. Система должна формировать отдельный campaign-level incident, а не только набор сырых findings.
8. Система должна выпускать не более одного campaign incident на одно окно для каждого scope анализа.
9. Система должна сохранять связь incident с исходными `requestId`, `sessionId`, `agentId` и, если доступно, `userId`.
10. Система должна предоставлять representative example запроса или эквивалентный explainability anchor для расследования.
11. Система должна уменьшать alert fatigue за счёт объединения однотипных PI-сработок в один operational signal.
12. Система должна быть пригодна для replay-проверки на воспроизводимых сценариях.

## Требования к данным

Для участия события в campaign-анализе должны быть доступны:

- `eventTime`;
- `requestId`;
- `sessionId`;
- `guardrailName = PROMPT_INJECTION`;
- `triggered = true`;
- embedding исходного пользовательского запроса.

Дополнительно для расследования и explainability должны быть доступны:

- полный текст исходного пользовательского запроса;
- `confidence` исходного finding;
- `agentId`;
- `userId`, если он есть в потоке.

## Требования к конфигурации

Параметры campaign detection должны задаваться в `YAML`.

Минимально конфиг должен поддерживать:

- `enabled`;
- `mode: GLOBAL | PER_AGENT`;
- `window`;
- `minGroupSize`;
- `topKSeeds`;
- `maxCosineDistance`;
- `severityByGroupSize`.

Стартовое значение `minGroupSize` для MVP:

- `3`.

Пример конфигурации:

```yaml
promptInjectionCampaign:
  enabled: true
  mode: GLOBAL
  window: 5m
  minGroupSize: 3
  topKSeeds: 3
  maxCosineDistance: 0.12
  severityByGroupSize:
    low:
      min: 3
      max: 4
    medium:
      min: 5
      max: 7
    high:
      min: 8
      max: 11
    critical:
      min: 12
```

## Требования к severity

`Severity` должна определяться конфигурацией и зависеть только от размера найденной группы.

Для MVP severity mapping должен задаваться в `YAML` через `severityByGroupSize`.

## Требования к выходному incident

Campaign incident должен содержать как минимум:

- `incidentType`;
- `detectionMode`;
- `windowStart`;
- `windowEnd`;
- `groupSize`;
- `uniqueSessionCount`;
- `requestIds`;
- `sessionIds`;
- `severity`;
- `representativeRequest`;
- `explanation`.

Дополнительно:

- для `GLOBAL` — `agentIds`;
- для `PER_AGENT` — `agentId`;
- при наличии — `userIds`.

## Требования к доступности результата

Campaign incidents должны быть доступны:

- в Grafana как новый тип incident;
- через `REST` API для получения списка активных incidents;
- через `REST` API для просмотра содержимого конкретного incident.

`REST` API MVP должен возвращать только активные incidents.

## Требования к доступу и retention

Полный текст пользовательского запроса и `representativeRequest` должны считаться чувствительными данными.

Для них должны быть зафиксированы отдельные правила:

- доступ только для `privileged` роли;
- отдельный retention policy;
- отдельный access control для `REST` и UI-представления.

## Нефункциональные требования

1. Решение должно укладываться в текущую near-real-time модель MVP.
2. Логика должна быть достаточно простой для объяснения risk-команде, аудиторам и стейкхолдерам.
3. Первая версия не должна требовать отдельной тяжёлой ML-платформы.
4. Поведение детектора должно быть детерминированным и воспроизводимым на одинаковом входе.
5. Работа с полным текстом запроса должна учитывать agreed access-control и retention semantics.

## Критерии готовности

Capability считается готовой для MVP, если:

1. На replay-сценарии согласованной атаки система поднимает campaign-level incident.
2. На одиночных и несвязанных PI-сработках система не формирует такой incident либо делает это заметно реже.
3. Аналитик с `privileged` доступом может перейти от incident к связанным `requestId`, `sessionId`, `agentId` и полному тексту representative prompt.
4. В Grafana виден новый тип incident и его базовые характеристики.
5. Через `REST` можно получить список активных campaign incidents и содержимое конкретного incident.
6. Параметры чувствительности и severity настраиваются через `YAML`.
7. Команда может показать практический business outcome: обнаружение повторяющейся атаки, а не только рост числа PI-findings.

## Ограничение MVP по числу incidents на окно

В пределах одного окна для каждого scope анализа выпускается не более одного campaign incident.

Это ограничение выбрано осознанно, чтобы:

- упростить operational semantics;
- уменьшить число дублей;
- сохранить explainability первой версии;
- не смешивать MVP с multi-campaign decomposition.

Возможность нескольких независимых campaign incidents в одном окне рассматривается как дальнейшее расширение, а не как часть первой версии.
